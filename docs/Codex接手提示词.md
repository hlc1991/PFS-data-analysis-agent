# Codex 接手提示词

## 使用方法

1. 将源码 ZIP 解压到新的开发目录。
2. 使用 Codex 打开解压后的项目根目录。
3. 将下面“可直接复制的提示词”完整发送给 Codex。
4. 第一轮只要求 Codex盘点、验证和汇报；看完报告后，再让它开始具体开发。

## 可直接复制的提示词

```text
你现在接手 PFS 数据分析 Agent 项目。请把当前打开的目录视为项目根目录，先建立可靠的开发基线，再进行任何功能修改。

项目定位：
PFS 数据分析 Agent 是一款本地智能分析工作台，支持自然语言分析、受控数据查询、图表生成、多格式报告交付和结果历史回看。

固定产品边界：
1. 商业画布和 Google Sheets 已明确退役，不得重新加入产品入口、默认工具或发布材料。
2. MCP、Teams、Hooks、飞书是可配置扩展能力；是否可用取决于具体账号、凭据、权限和网络环境。
3. 云端登录与 GPU/远程执行默认关闭，没有明确需求和目标环境时不要启用。
4. 当前版本不支持用户图片上传与视觉分析。
5. 不得提交 .env、API Key、Token、数据库、用户上传、业务原始数据、输出、日志、缓存、虚拟环境或 node_modules。
6. 保留 LICENSE、NOTICE.md 和适用的第三方许可证，不要错误声明第三方代码的权利归属。

第一步：只读接手审计
请完整阅读并遵守根目录 AGENTS.md，然后依次阅读：
- docs/HANDOFF.md
- docs/FUNCTION_COMPATIBILITY_MATRIX.md
- docs/PFS数据分析Agent产品说明书.md
- docs/PFS数据分析Agent项目技术文档.md
- README.md
- PRODUCT.md
- Information/Instruction.md

随后完成以下只读检查：
1. 列出项目主要目录、启动入口、技术栈和配置入口。
2. 检查当前是否存在 .git；如果没有，不要自行连接旧仓库。
3. 检查工作目录中是否存在密钥、数据库、上传数据、输出、缓存和本地配置残留。
4. 核对文档中的启动命令、默认端口、Node/Python 版本和代码实际配置。
5. 核对商业画布与 Google Sheets 是否确实退出入口和默认能力。
6. 核对 MCP、Teams、Hooks、飞书、云登录和 GPU/远程执行的默认状态，但不要发起真实外部调用。

第二步：建立可运行基线
在不修改业务逻辑的前提下：
1. 安装项目依赖。
2. 启动本地服务并检查 http://127.0.0.1:5001。
3. 运行 Python 测试、Ruff、Prettier、ESLint、前端构建检查和 git diff 检查。
4. 使用 data/fixtures/pfs_sales.csv 完成一次核心 smoke：新建会话、连接数据、读取结构、按地区汇总销售额、生成图表、下载结果、历史回看。
5. 如果没有真实模型凭据，明确区分确定性固定样例验证和真实模型验证，不要把前者描述为后者。

第三步：给我接手报告
报告必须结论先行，并按以下格式输出：
- 当前能否启动和完成核心分析闭环
- 已验证的功能及证据
- 未验证、待配置或默认关闭的能力
- 文档与代码不一致之处
- 安全或交接残留
- 新仓库建立前必须处理的问题
- 建议的前三个开发切片及优先级

工作规则：
- 第一轮不要删除、重命名、大范围重构、提交、推送、创建 Release 或调用外部服务。
- 遇到问题先定位根因并提供证据，不要为了通过测试而删除测试、降低校验或隐藏错误。
- 修改必须以小切片进行，保留现有行为并增加针对性回归验证。
- 严格区分代码存在、本地测试、本地运行、真实模型、CI、安装包、实机验证、Release、部署和线上可用。
- 发现文档冲突时先报告；得到确认后再修改权威文档。
- 完成只读审计和基线验证后停止，等待我确认下一项开发任务。
```

## 建立新仓库后的第二条提示词

```text
现在已为 PFS 数据分析 Agent 建立新的 Git 仓库。请先读取 AGENTS.md、docs/HANDOFF.md 和 docs/FUNCTION_COMPATIBILITY_MATRIX.md，检查当前分支、远端、工作区差异和最新提交。

请完成新仓库基线收口：
1. 更新 README 中的仓库地址、Release 地址和维护者信息，不改变产品范围。
2. 检查 .gitignore，确保密钥、运行数据、上传、输出、数据库、缓存、虚拟环境和依赖目录不会被提交。
3. 配置或检查 GitHub Actions，使 Python 测试、Ruff、Prettier、ESLint 和前端构建检查覆盖当前提交。
4. 运行完整质量门并给出实际结果。
5. 审查待提交差异，列出每个文件的作用和风险。

未经我明确授权，不要 commit、push、创建 Release 或删除文件。完成后只汇报当前状态、差异、验证结果和建议的下一步。
```
