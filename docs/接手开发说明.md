# PFS 数据分析 Agent 接手开发说明

> 适用对象：后续项目负责人、开发人员及其 Codex。
> 交接日期：2026-09-10。
> 使用原则：先建立可复现基线，再进行功能开发；任何新结论都以接手环境中的实际运行结果为准。

## 一、项目是什么

PFS 数据分析 Agent 是一款本地智能分析工作台，支持自然语言分析、受控数据查询、图表生成、多格式报告交付和结果历史回看。

当前产品边界：

- 核心范围：结构化数据文件、数据库和受控数据源的数据理解、查询、分析、可视化与结果交付。
- 明确退役：商业画布、Google Sheets。
- 可配置扩展：MCP、Teams、Hooks、飞书。
- 默认关闭：云端登录、GPU/远程执行。
- 当前不支持：用户图片上传与视觉分析。

## 二、交接文件夹怎么使用

交接文件夹按编号组织：

1. `00_交接说明/`：先阅读这里。包含项目规则、当前状态、能力矩阵、验收清单和合规文件。
2. `01_项目源码/`：源码 ZIP 是新仓库的代码基线；同目录的 `.sha256` 用于核对文件完整性。
3. `02_产品与技术文档/`：产品说明书用于理解产品价值和用户流程，技术文档用于理解架构和维护方式。
4. `03_安装包/`：提供 Windows x64 安装包及校验值；本次交接不提供 macOS 安装包。
5. `04_演示与测试材料/`：包含演示视频、演示脚本和脱敏示例数据。

建议保留原交接文件夹作为只读备份，在另一个开发目录解压源码，不要直接在 ZIP 或交接原件中开发。

## 三、接手操作顺序

### 1. 校验并解压源码

先核对：

```bash
shasum -a 256 -c PFS-data-analysis-agent-handoff-20260910.zip.sha256
```

Windows PowerShell 可执行：

```powershell
Get-FileHash .\PFS-data-analysis-agent-handoff-20260910.zip -Algorithm SHA256
```

将 ZIP 解压到一个新的开发目录。源码包不含 `.git`，接收方可在验证通过后建立自己的仓库。

### 2. 让 Codex 建立项目上下文

在 Codex 中打开解压后的项目根目录，将 `00_交接说明/Codex接手提示词.md` 中的提示词完整发送给 Codex。

Codex 应先进行只读盘点，不应一开始就重构、删除文件、提交或推送。

### 3. 阅读权威入口

按照以下顺序阅读：

1. 根目录 `AGENTS.md`
2. `docs/HANDOFF.md`
3. `docs/FUNCTION_COMPATIBILITY_MATRIX.md`
4. `docs/PFS数据分析Agent产品说明书.md`
5. `docs/PFS数据分析Agent项目技术文档.md`
6. `README.md`、`PRODUCT.md` 和 `Information/Instruction.md`

如文档与当前代码或实际运行冲突，应记录差异并以当前代码和重新验证结果为准，不要静默覆盖文档。

## 四、建立本地开发环境

### macOS/Linux 源码环境

需要 Python 3.10+、Node.js 20.19+ 和 pnpm。

```bash
./install.sh
./start.command
```

或者在依赖已经安装时：

```bash
.venv/bin/python app.py
```

### Windows 源码环境

需要 Python 3.10+、Node.js 20.19+ 和 pnpm。

```powershell
powershell -ExecutionPolicy Bypass -File .\install.ps1
.\start.bat
```

启动后访问：

```text
http://127.0.0.1:5001
```

模型、数据库和外部服务的密钥不在交接包中，必须使用接收方自己的账号和凭据重新配置。

## 五、接手后的第一轮验证

### 1. 代码质量门

macOS/Linux：

```bash
PYTHONDONTWRITEBYTECODE=1 .venv/bin/python -B -m unittest discover -s tests -p 'test_*.py' -q
.venv/bin/ruff check .
pnpm run format:check
pnpm run lint
pnpm run build:check
git diff --check
```

Windows、macOS 和 Linux 上可直接使用 `pnpm run quality` 执行前端检查、Python 测试与 Ruff；该入口自动选择项目虚拟环境并启用 UTF-8。

Windows 应执行等价的 Python、Ruff、pnpm 和 Git 检查。若接收环境与交接环境不同，应记录版本和失败原因，不要为了通过检查而删除测试或降低规则。

### 2. 核心功能 smoke

使用仓库中的 `data/fixtures/pfs_sales.csv`，或交接文件夹中的 `04_演示与测试材料/Sample-data.xlsx`：

1. 新建会话。
2. 上传并连接示例数据。
3. 查看表、字段、行数、数据范围和数据质量提示。
4. 提问：`按地区汇总销售额，并说明哪个地区最高。`
5. 生成一张地区销售额图表。
6. 下载 JSON、CSV 或 Excel 结果。
7. 在任务历史中重新打开本次运行和交付物。

只有完成这一闭环，才能称接手环境中的核心能力已运行正常。

### 3. Windows 安装包验证

1. 校验 `PFSDataAnalysisAgent-Windows-x64.exe.sha256`。
2. 在 Windows x64 实机安装并启动。
3. 完成新建会话、示例数据上传、一次分析和历史回看。

现有安装包只能证明现有发布产物；后续代码修改后必须从新仓库对应提交重新构建安装包。

## 六、建立接收方的新仓库

建议在源码验证通过后再初始化仓库：

```bash
git init
git add -A
git commit -m "Initial PFS Data Analysis Agent baseline"
git branch -M main
git remote add origin <接收方的新仓库地址>
git push -u origin main
```

建立仓库时还应：

- 更新 README 中的仓库地址、Release 地址和维护者信息。
- 配置 GitHub Actions，并确认 CI 对应当前提交 SHA。
- 保留 `LICENSE`、`NOTICE.md` 和适用的第三方许可证。
- 不提交 `.env`、密钥、数据库、上传数据、输出、缓存、虚拟环境或依赖目录。
- 新版本发布时记录提交 SHA、CI、安装包校验值和实机 smoke 结果。

## 七、后续开发规则

1. 修改前先查看仓库状态和相关代码，不覆盖他人的未提交工作。
2. 每个改动以小切片完成：定位问题、增加或更新测试、实现修改、运行专项测试、运行完整质量门。
3. Agent Loop、工具调用、数据连接和结果交付属于核心链路，不能在缺少回归验证时大范围重构。
4. SQL 失败后成功重试的过程可以保留，但最终界面应清楚区分中间尝试和最终失败。
5. 外部模型、MCP、Teams、Hooks、飞书、云登录和远程 GPU 必须在具体账号、网络、权限和目标环境中分别验证。
6. 商业画布和 Google Sheets 不得重新进入产品入口、默认工具和发布说明，除非产品范围被正式重新决策。
7. 产品范围、默认开关、验证状态或发布状态发生变化时，同步更新 `docs/HANDOFF.md` 和 `docs/FUNCTION_COMPATIBILITY_MATRIX.md`。
8. 必须区分“源码存在、测试通过、本地运行、CI 通过、安装包生成、实机通过、Release 发布、线上可用”等状态。

## 八、建议的首周开发安排

1. 第一天：完成环境安装、代码质量门和核心 smoke，形成接手基线记录。
2. 第二天：建立新仓库和 CI，处理 README 中的新仓库信息。
3. 第三天：选择一个真实使用问题，以最小切片修复并补回归测试。
4. 后续：按功能矩阵逐项维护；需要外部账号的能力保持“待配置”，不要在没有证据时改为“已验证”。

## 九、遇到问题时怎么判断

- 页面打不开：先检查应用是否启动、端口是否被占用、健康接口和启动日志。
- 数据无法分析：先检查数据源连接、表名、字段类型、Schema 和只读 SQL。
- Agent 重复说“正在处理”却无结果：检查 SSE 事件、工具调用结果和停止条件，不要只改前端文案。
- 某次 SQL 报错但最后有结果：确认是否为模型修正查询后的成功重试；只有最终没有可用结果时才判定本轮失败。
- 外部能力不可用：先确认是否配置了对应账号、凭据、权限和网络，再区分代码问题与环境问题。

## 十、交接完成标准

接收方完成以下事项后，可认为开发交接完成：

- 源码校验通过并可在接收环境启动。
- 完整质量门通过，或失败项已有明确环境原因和处理计划。
- 核心数据分析闭环运行成功。
- 接收方的新仓库已建立，首次提交和 CI 对应一致。
- 已明确当前功能范围、默认关闭能力和未验证外部能力。
- 接收方知道如何开发、验证、构建和发布后续版本。
